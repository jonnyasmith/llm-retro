# The persisted Job run is authoritative for a run's state, and every watcher is given a snapshot first

A Job run's state is observable from two places — the persisted Job run record, and the in-process event source the dispatcher emits to — and they do not agree. Only the record can express `interrupted`, because a run left mid-flight is recognised as interrupted by a **later process** at start-up (domain: Job run), long after the crashed process's events ceased to exist. We therefore make the **persisted record authoritative** for a Job run's status and progress, treat the event source purely as a low-latency delta channel, and merge the two behind a single module so that every watcher — the browser today, any other transport later — is given a **Job run snapshot** as its first event and deltas thereafter.

## Considered options

- **Emit `interrupted` into the event source during start-up reconciliation**, so the event source alone is the source of truth. Rejected: those correlation ids belong to a dead process, no watcher is subscribed at start-up, and the events would sit in a bounded in-memory ring purely on the chance someone reconnects. It fabricates liveness for a fact that is inherently historical.
- **Let each consumer reconcile the two sources itself.** This is what the code did, in three places — the stream route synthesised two events, and the browser re-derived the same state a third time from server-rendered data. Rejected on evidence: the duplication was already real, not hypothetical, and the browser's copy silently disagreed with the server's.

## Consequences

- **Historical progress deltas are never replayed.** The dispatcher writes the Job run record *before* it emits the matching progress event, so the record always dominates every progress event still held in memory. A snapshot therefore makes replayed progress redundant by construction. This is what allows the monotonicity clamp — previously invented, undocumented, at the browser leaf — to be deleted rather than relocated. Anything a snapshot cannot carry is lost on reconnect until the next live delta; the current file being processed is the only such field, and it is not persisted.
- **Log lines are best-effort and explicitly not durable.** They live only in a bounded in-memory ring and are evicted silently. This is a deliberate entitlement decision, not an oversight: making a Job run's log complete would mean persisting it. The retained-line bound is published as part of the stream contract so both sides use one number.
- **A snapshot resets whatever a watcher derived before it.** Because logs replay on every connection, a watcher must discard its accumulated view when a snapshot arrives. Tying the reset to the snapshot rather than to a transport connection event keeps the rule inside the contract, where both sides can be tested against it, instead of being a convention two files honour by luck.
- **The first event is always a snapshot, with no exceptions** — including for a run that is already finished, which receives a snapshot immediately followed by its terminal event. The redundancy buys the contract its only unconditional promise, so no consumer needs a branch for "did I get a snapshot".
- This discharges ADR-0004's containment claim, which was previously false. It does not revisit the choice of Server-Sent Events; the transport remains replaceable precisely because the merge no longer lives inside the route.
