# 01 — App skeleton, boot sequence, and test harness

**What to build:** A running single-process app that serves the UI and API and owns a live SQLite database. Starting the app opens one shared database connection, applies any pending migrations, and initialises the singleton owners of long-lived state — so that everything built later has a booted process, a current schema, and a test setup to hang off. A developer can start the app, see it serve a trivial health route that confirms the database is connected, and run the test suite against a throwaway database.

**Blocked by:** None — can start immediately.

**Status:** ready-for-agent

- [ ] SvelteKit + TypeScript app builds and runs as one long-lived process via `adapter-node` (no static/serverless adapter).
- [ ] Drizzle over the synchronous `better-sqlite3` driver is wired; the connection is a module singleton created once at server startup.
- [ ] The database lives in a conventional app data directory, overridable by a single environment variable (used by tests/dev for throwaway databases).
- [ ] WAL mode is enabled on the connection.
- [ ] Boot sequence runs before the app serves requests: open connection → apply pending migrations → (reconciliation and job-runner init land in later tickets, leave the seam) .
- [ ] Migrations are generated by `drizzle-kit` and committed to the repo; pending ones auto-apply at boot.
- [ ] A trivial health route confirms the process serves both UI and API and that the database connection is live.
- [ ] Vitest is set up and runs against a fresh temporary database via the data-dir env override; an example integration test proves the harness works.
